# Teams 群组通信 v1 审计反馈与修订合同

日期：2026-10-21（America/Los_Angeles）。

对象：`docs/design/teams-group-messaging-v1.md`、其 manifest 和 7 个设计 DAG。
本文件记录审计反馈和随后用户确认的语义，不表示原设计已经修订或实现已经交付。
本轮只读核对设计、DAG、现有 Relay/注册客户端、ACP Host 和架构映射；未重跑图校验或运行验收。

## 1. 审计结论与范围

星型 Relay、复用现有 WSS/TLS、Console 不进数据路径、Tailscale 外部管理的方向保留。
原稿尚不能直接进入模块实现。先修订 issue/action、生命周期、授权、可靠投递和 Session 契约，再更新受影响 DAG 与验收。

本次只要求设计修订，不实现业务代码，不启动服务，不部署，不改写项目需求，不新增无关治理。
没有执行路径的本反馈文档不新建 DAG；原设计的 7 个业务 DAG 必须按修订后的语义检查闭合。

## 2. 用户已确认的语义（修订时必须落实）

### 2.1 群可见性与响应责任

- 消息属于群空间。广播、@ 单人或多人均在群内可见，@ 不是私聊。
- 发送工具必须以参数明确行动对象、是否要求回复、是否为追加，以及各自的具体原因。不能从正文猜测。
- 消息投递对象与承担行动的人是不同概念。旁观成员不因收到消息而启动模型回合。
- 普通消息、进展、答复和评论不自动创建新的行动责任。

### 2.2 issue 与会话生命周期

- 一个会话绑定一个 Vikunja issue。bug、讨论、审计和执行事项都必须可追踪。
- Vikunja 是 issue 及其 open/closed 状态的唯一真源。Teams 会话状态是本地投影，不独立修改。
- 会话发起者负责关闭。关闭会话必须成功关闭对应 issue，并记录关闭原因与结果依据。
- 重开同一个会话必须成功重开原 issue，记录原因，沿用原会话和历史。
- action 完成不等于 issue 或会话关闭。其他参与者可以建议关闭，由发起者执行。
- 关闭后迟到内容只留历史，不触发行动，不自动重开。
- 发起者通过 Vikunja 直接关闭或重开时，Teams 也必须收敛到同一状态。身份映射与权限必须支持此约束。

### 2.3 发起、行动、回复与追加

每次发起行动至少明确：认证发起人（默认被回复者）、issue、action、具体原因、要求谁行动、预期结果、是否要求回复及原因。

每个 action 有稳定 actionId，属于一个 issue；答复关联原 action。需要追问时创建新的显式 action，并关联先前 action 或评论，不重新激活已经完成的行动。

支持讨论型 issue：发起者邀请指定成员讨论、comment 或审计。参与者将评论、意见或审计结果补充到对应 Vikunja issue 后，本人的 action 即结束。无需等待其他参与者完成，也不自动继续往返。发起者阅读后，可以关闭 issue，或带具体原因向指定成员发起追问。

工具应区分以下操作，不要求机械采用这些名称：

| 操作 | 必须明确的内容 | 结束语义 |
| --- | --- | --- |
| 创建/发起 | 问题、原因、发起人、行动对象、行动、结果要求 | 创建 issue 或在已有打开的 issue 下创建 action |
| 回复/提交结果 | 原 action、内容、依据、是否要求进一步行动及原因 | 完成本次责任；不自动启动对方 |
| 追加/comment | 追加内容、原因、是否要求行动及对象 | 纯补充不触发执行；要求行动则显式创建 action |
| 追问 | 原问题/结果引用、追问原因、对象、答复要求 | 创建新的有限 action |
| 关闭 | 发起人身份、原因、结论、依据、未完成行动的处置 | Vikunja 成功关闭后确认会话关闭 |
| 重开 | 发起人身份、原因、剩余问题及行动 | Vikunja 成功重开后恢复原会话 |

“内容已发到 Relay”和“结果已补充到 Vikunja”是不同回执。对于 comment/审计 action，只有必要结果成功写入 issue，才能报告该 action 已完成；写入失败必须显式保留待处理状态。

### 2.4 master/peer 的不对称权限

- peer 可以要求 master 回复或行动。master 可以拒绝，但必须说明具体原因。
- master 对 peer 的有效指派，peer 不能主动拒绝。
- peer 可以报告缺少信息、阻塞或执行失败，必须给具体原因与证据；不能据此自行关闭 issue 或免除责任。master 决定补充、调整、取消或重新指派。
- master 拒绝一个 action 只结束该 action，不自动关闭 issue。
- 角色不能绕过系统权限、安全限制或未授予的能力。超出执行边界要返回明确错误，不伪装成功。
- 必须明确谁是谁的 master，不能仅凭群内角色名称推导指挥权；群管理权、行动指挥权和 issue 关闭责任分开。
- peer→peer、多个 master 的关系及冲突处理尚未由用户定案。设计应提出最小建议并标明待决定，不伪称已有授权。

## 3. 必须修正的设计缺口

### 3.1 消除自动互答

删除“每次群消息注入完成就发送普通回复并再次被注入”的隐式链。只有明确指定接收者的 action 才启动处理。完成、评论、进展和关闭通知只更新记录；新的追问才创建下一项行动。广播要求多人行动时，为每人记录独立责任；一人完成不能关闭其他人的行动。

### 3.2 可靠投递与幂等

第一批必须定义以下边界，不能留给模型接入阶段：

- hub 的发送成功回执表示消息已经持久接受，不表示接收或执行成功。
- 稳定提交标识跨重连不变；同标识同内容返回原回执，内容冲突显式失败。requestId 是否兼任此用途要写清。
- 明确 daemon ACK 的可靠接管点。建议本地持久 inbox 成功后 ACK；执行与结果提交另记状态。
- 补投可以重复，接收方按稳定标识去重。不能承诺跨任意引擎副作用的恰好执行一次。
- 引擎执行期间崩溃、执行成功但结果未提交等情况要有结果未知边界和恢复责任，不能盲目重跑。
- 累计水位只能越过已经安全处理或明确不适用的项。明确过滤、并行、重连、成员加入/退出/重入的规则。
- 保留上限与容量必须确定；水位落后于保留起点时显式报告历史缺口，禁止静默跳过。

### 3.3 关闭、在飞行动与外部写入

关闭前必须明确处置未完成行动。未开始行动取消；在飞行动进入取消或收口，已有副作用保留事实。issue 已关闭不代表物理执行已经停止，两者分别报告。

定义关闭期间新 action 的准入、外部关闭事件、迟到提交和重开后的旧 action 处理。旧 action 不因重开自动重跑。

Vikunja 不可用时，关闭/重开不得伪造成功；已有未受影响工作按声明契约继续。定义变更结果未知时的回读和重试边界，防止重复评论、重复 issue 和重复行动。

### 3.4 本地 Session 与抢占

明确 group、issue/会话、本地 ACP Session、action、prompt 的映射，不把共享逻辑会话等同于跨 agent 共用一个 ACP Session。原文“一个 group 一个会话”必须按 issue 会话语义修订；同一 group 可以包含多个 issue。

现有 `agent-host/acp-host.ts` 使用 channel.activePrompt 和 Session 归属校验，不能直接据此声称已有完整的 group/issue 关联。

规定 Session 创建、恢复、引擎重启、能力不支持时的行为。取消请求发出后须等待原 prompt 终结，再发新 prompt。steer 是请求，接收 agent 按本地授权决定是否可抢占；不能取消无关人类会话或其他 issue 的行动。

### 3.5 成员与访问控制

补充创建、邀请、接受、离开、角色授予、群主管理、历史读取、追问和关闭的权限矩阵。入群与行动接受分开；peer 不能拒绝指派不等于不能拒绝入群。

在线推送、历史查询和离线补投使用相同成员/作用域约束。定义新成员历史可见范围和退出后的访问撤销。inReplyTo/action 引用须属于允许访问的 issue 与群。

### 3.6 连接与协议的真实接线

daemon 当前通过 RegistrationClient 组合注册连接，该接口尚未暴露群请求和群事件。只扩展 relay-client.Event 不足以让 runtime 使用通道。

设计须覆盖现有注册连接接口、请求关联、推送分派、错误回执、重连订阅及 runtime 组合。不得新建第二个 Relay socket 绕过 owner。

`relay.message.page` 要有查询入口；msg inbox、未读数及 issue/action 查询必须有明确来源。新回复帧也要接入关联分派，不能只增加两个事件联合成员。

定义共用连接上的群消息背压与错误隔离，避免非关键业务处理错误拖掉目录和心跳。

### 3.7 持久化与所有权

建议使用 registry 的 dataDirectory 作为持久根，默认路径可落在 ~/.agentteams。不要让多个 daemon 因账户相同共写硬编码目录。

JSONL 可保留，但须规定单写者、序号恢复、尾部半行、磁盘满和持久成功边界。“一条消息一行”本身不能证明每条消息的投递；消息接受、水位和执行结果的证据分开。

Vikunja 拥有 issue；Teams 拥有 action、消息与执行记录。关键 action 的发起、对象、原因和终态须在 issue 可追踪，详细日志通过稳定引用关联。不得保留第二套可独立修改的 issue 状态或任意双向覆盖。

### 3.8 Vikunja 接入与 CLI

Vikunja 最小能力必须前移，不再完全属于第三批：创建/引用 issue、读取状态、提交 comment/结果、关闭/重开及身份映射。

需要版本化核实 API、状态映射、权限、webhook 签名和私网约束。原文“绑定局域网地址即可解决私网 webhook 限制”不能作为已确认结论；局域网地址仍可能被拒绝。不得把配置建议当已验证事实。

join 明确已有配置和 daemon 时的行为、配置写入 owner、凭据来源、启动失败的保留状态及 CLI 选择哪个 daemon。复用现有生命周期，不隐式重建或启动第二个 daemon。

## 4. DAG 与分批修订

现有 7 个图都是成功直链。结构 SESE 不证明失败、拒绝、等待与重入语义完整。按受影响对象流修订，不为覆盖而堆图。

- 邀请与成员响应是两个异步事件，各自应有持久回执，不悬挂为一次连续执行。
- 一次投递尝试应在 ACK、离线、超时或断连等明确结果处结束；后续补投是新事件。
- 注入须覆盖排队、权限拒绝、取消、不支持、执行失败及未知结果。
- 加入 issue/action 发起、评论落盘、追问、关闭和重开的真实外部边界；失败与等待可用 typed outcome 收敛到唯一出口。
- 明确关闭与在飞 action 的收口，不用成功直链掩盖未停止的执行。
- 更新实际受影响的架构映射和 gate 设计，不能只从 module-registry 开始把未闭合语义固化为模块。

建议增量：

1. 基础闭环：Vikunja 最小 issue 生命周期、action 契约、成员权限、群消息持久接受/去重/可靠接管，以及本地 CLI。先以人工提交评论/结果证明完整闭环。
2. 模型执行：ACP Session 映射、queue/steer、讨论/comment/审计 action、结果写回、关闭后的取消与收口。
3. 增量能力：Vikunja 事件通知与状态收敛的完善、部署验证及实际需要的扩展。不能把前两批所需的关闭与状态可见性推迟到本批。

## 5. 必须覆盖的验收场景

- 群内 @B：A/B/C 都可见，仅 B 承担行动；普通旁观者不启动模型。
- 讨论 issue 指定 B/C：各自提交 comment/审计到 Vikunja 后结束；无人自动互答；发起者可以显式追问，再关闭。
- peer 请求 master：master 可以带原因拒绝；master 指派 peer：不能主动拒绝，阻塞/失败有依据且由 master 处置。
- 多人 action 独立完成；一人的结果不结束其他人的责任。
- 发送回执丢失重试不重复入账；hub/daemon 重启后不漏持久接管的消息；重复补投不重复启动行动。
- 结果写入 Vikunja 失败或回执丢失时不伪报完成，不重复追加结果。
- 关闭 Vikunja 失败时会话仍未确认关闭；成功后迟到消息不触发执行。
- 发起者在 Vikunja 关闭/重开，Teams 状态正确收敛；重开不重跑旧 action。
- 关闭时队列行动取消，在飞行动收口与物理停止状态如实报告。
- 越权指派、跨群引用、离群历史访问被拒绝；能力不足不伪装成功。
- queue 不抢占；steer 等待取消终结；无关人类 Session 不受影响。
- 缓存容量或保留期造成历史缺口时显式可见。
