AgentTeams 本地 MVP：如何交付、如何测试

这份页面给出可执行的交付路径、分层测试入口，以及最终验收矩阵。所有命令都可在仓库根直接运行。

交付形态

一个 npm 安装包。它包含 agentteams CLI、Console 静态资源、编译后的 runtime 库和 DAGpipe runner。 用户从源码树外安装，只编辑 ~/.agentteams/config.toml。

交付 = 代码进入 origin/main，并给出远端回执。安装包是构建产物，不提交。

第 1 步

构建可安装包

安装依赖，再生成 final 模式的包与它的身份 receipt。

pnpm install --frozen-lockfile
pnpm build:governance

产物：generated/modules/teams-source/lib
身份：generated/modules/teams-source/package-receipt.json 里的 head_commit / base_commit / content_sha256。

第 2 步

打包并安装到源码树外

用真实 tarball 安装。这一步证明包可以离开源码树运行。

npm pack generated/modules/teams-source/lib \
  --pack-destination /tmp/at-pack --json

npm install --prefix /tmp/at-prefix --no-audit --no-fund \
  --no-package-lock --no-save /tmp/at-pack/agentteams-0.1.0.tgz

可执行文件：/tmp/at-prefix/node_modules/.bin/agentteams

第 3 步

首次运行

用户只写一份可编辑配置。系统状态放在 internal.toml，用户不改。

agentteams init   --config ~/.agentteams/config.toml
agentteams start  --config ~/.agentteams/config.toml
agentteams status --config ~/.agentteams/config.toml
agentteams console start --config ~/.agentteams/config.toml
agentteams stop   --config ~/.agentteams/config.toml --generation <n>

Console 是可选的观察面。关闭 Console 后，新的 Agent Work 仍然成功。

集成与回执

git push origin main
git ls-remote origin refs/heads/main

远端返回的 SHA 必须等于本地 git rev-parse HEAD。本地干净检查用 git status --short，输出为空才算干净。

分层测试阶梯

按风险选层，不逐次跑全套。提交动作本身不触发整套测试。

阶段入口证据何时选它

pnpm verify 展开是什么
pnpm test && pnpm typecheck && appsdk guide compile && appsdk compile && pnpm smoke && appsdk verify
其中 pnpm test = pnpm build:runtime && pnpm --dir opencode-adapter build && node scripts/regression.mjs。

跑最终验收

这是「安装后的真实业务入口」验收。它从一个安装包跑完 14 个 case，覆盖 U1–U7 与 D3/D4。

pnpm build:governance

node scripts/blackbox-user-mvp.mjs --case all \
  --package generated/modules/teams-source/lib \
  --evidence-dir /tmp/at-evidence/all \
  --receipt /tmp/at-evidence/all.receipt.json

退出码怎么读

  • 0 全部通过
  • 1 有 case 失败
  • 2 有 case 未验证（环境缺前置）

receipt 里的 exit.failed 与 exit.unverified 分别列出失败和未验证的 case。

只看一个 case

node scripts/blackbox-user-mvp.mjs --list
node scripts/blackbox-user-mvp.mjs --case BB04 \
  --package generated/modules/teams-source/lib \
  --receipt /tmp/at-evidence/bb04.receipt.json

先 --list 看 case 编号，再用 --case 单选或多选（逗号分隔）。

每个 case 做什么

BB01–BB12、BB14 走安装副本的真实入口：npm pack/install 到源码树外、真实 Camo 浏览器、真实 installed Console、真实 provider、真实 managed OpenCode 的 message/tool/permission/cancel。 BB13 是治理 case：它在候选克隆里跑真实 lifecycle adapter，再依次改动 source/graph/config/artifact/evidence 输入，验证恢复与失效边界。

三条已知边界

1. BB13 内部门禁有一次负荷抖动。 在 68c7fbe 的重跑里，BB13 克隆内的 pnpm verify 有 1/776 例失败： runtime/managed-opencode-session.spec.ts 的真实 OpenCode 往返用例实测 11.92 s，超过它自己的 10 s 预算。 该用例单独跑三次是 1.95 / 1.99 / 1.95 s，且在更早的 BB13（8 次 verify）里全通过。 这是满负荷下的时序敏感，不是产品缺陷。超时与断言都未放宽；既有 issue 5abd96e 继续跟踪。
2. 包内容哈希跨构建不可复现。 同一提交连续三次 pnpm build:governance 得到三个不同的 content_sha256。 逐文件比对定位到只有 runtime/dagpipe/bin/darwin-arm64/agentteams-dagpipe-runner 与其 manifest 每次不同，原因是本地 Rust 链接产物非确定（macOS 链接 UUID）。 所以「同一个安装包」由验收 receipt 绑定的那次产物加候选提交界定，不能用跨构建哈希比较。
3. Relay 路径仍有一个 open P1。 issue 4e04166（Relay admission grant 到期会终止进行中的浏览器 Work）未收口。 它属于 Relay 路径；已交付的本地 Phase 1 路径由 BB03/BB06 的真实浏览器 Work 覆盖并通过。
