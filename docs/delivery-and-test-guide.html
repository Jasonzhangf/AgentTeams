交付形态

一个 npm 安装包。它包含 agentteams CLI、Console 静态资源、编译后的 runtime 库和 DAGpipe runner。 用户从源码树外安装，只编辑 ~/.agentteams/config.toml。

交付 = 代码进入 origin/main，并给出远端回执。安装包是构建产物，不提交。

功能说明：用户实际得到什么

功能 1 · 本地协作

两个独立 daemon 通过本地 bridge 协作

Provider daemon 发布能力和资源。Receiver daemon 发现 Provider，协商连接，并提交新的 Agent Work。Console 不是业务中继，关闭 Console 不会停止 Agent 协作。

用户样例：启动两个 daemon，receiver 请求 file-search，provider 执行搜索并返回真实结果。

功能 2 · 能力服务

Provider 声明 capability、operation 和 capacity

例如 file-search@1 的 search operation，以及容量为 2 的 search-slot resource。

用户样例：两个请求可以同时使用容量 2；第三个请求必须收到明确的容量不足错误，不会偷偷排队或切换能力。

功能 3 · DAGpipe Work

Work 从提交到业务结果完整执行

请求进入 Work submit，经过 capability matching、DAGpipe Operators、compile、immutable CompiledGraph、Runtime，最后由用户 query/open/request/close 消费业务结果。

用户样例：提交两个不同 marker 的 Work，得到两个不同真实结果；query 只读，不重复执行。

功能 4 · Console

Console 是可选的观察和配置面

Console 可以查看 Agent、provider、model、Work 和 Session 投影，也可以执行配置 CAS、Session message、permission 操作。

用户样例：Console stop 后继续用 CLI 提交新 Work；新 Work 仍成功。Console restart 后使用新的 generation。

功能 5 · OpenCode Session

LLM Agent 使用受管 OpenCode 执行 Session

Teams 不复制 LLM 请求栈。它选择明确的 provider/model，把 message、tool、permission、cancel 和 restart 事件投影给用户。

用户样例：发送 message，触发 tool，审批或拒绝 permission，再 cancel；没有真实确认的取消保持 unknown。

功能 6 · 生命周期保护

generation 和内部状态防止误杀、旧写入和资源泄漏

start、status、stop 都带有 launcher generation。旧 generation 的 stop 或配置写入会明确拒绝，不会停止当前 daemon。

用户样例：重复 start 失败；stale stop 被拒绝；正确 generation stop 后 daemon、socket、Console 和 child process 全部清理。

用户配置说明：只编辑 config.toml

用户配置唯一真源是 ~/.agentteams/config.toml。当前模板是 version 3。用户填写 bridge、Agent 角色、能力、连接目标和可选 Console 配置。internal.toml 是系统生成的运行状态，不是第二份用户配置。

# ~/.agentteams/config.toml
version = 3

[bridge]
enabled = true

# 发布能力和资源的 Provider Agent
[agents.provider]
enabled = true
role = "provider"
label = "Local provider"

[agents.provider.identity]
hostId = "local"
machineId = "local"
accountId = "local"
agentKind = "custom"
label = "Local provider"

[agents.provider.runtime]
scopeId = "local"
dataDirectory = "data/provider"
policy = { revision = 1, allowedConsumers = ["receiver"], allowedManagers = [] }
cli = { camoExecutable = "/path/to/camo", searchExecutable = "/opt/homebrew/bin/rg", searchRoot = "/path/to/files", profilePrefix = "teams-provider" }

[agents.provider.services.file-search]
version = "1"
operations = ["search"]
resources = [{ resourceId = "search-slot", capacity = 2, unit = "slot" }]

# 请求能力和执行 Work 的 Receiver Agent
[agents.receiver]
enabled = true
role = "receiver"
label = "Local receiver"

[agents.receiver.identity]
hostId = "local"
machineId = "local"
accountId = "local"
agentKind = "custom"
label = "Local receiver"

[agents.receiver.runtime]
scopeId = "local"
dataDirectory = "data/receiver"
policy = { revision = 1, allowedConsumers = [], allowedManagers = [] }
cli = { camoExecutable = "/path/to/camo", searchExecutable = "/opt/homebrew/bin/rg", searchRoot = "/path/to/files", profilePrefix = "teams-receiver" }

[agents.receiver.connect]
targetAgentId = "provider"
capabilityId = "file-search"
capabilityVersion = "1"
operation = "search"
demands = [{ resourceId = "search-slot", amount = 1 }]

# 可选。默认 false；打开后需要 username/passwordEnv。
[console]
enabled = false
# username = "teams-user"
# passwordEnv = "AGENTTEAMS_CONSOLE_PASSWORD"
配置区域字段含义
版本与 bridgeversion、bridge.enabled配置格式版本和本地 socket bridge 开关。当前用户模板使用 version 3。
Agent 基本信息enabled、role、labelprovider 发布能力；receiver 请求能力并消费 Work。
identityhostId、machineId、accountId、agentKind声明 Agent 身份和归属。它们不是凭据，也不代表网络授权。
runtimescopeId、dataDirectory、policy、cli声明运行范围、数据目录、允许的 consumer/manager，以及 provider 使用的本地工具路径。
Provider serviceservices.<id>.version、operations、resources声明能力版本、操作名和资源容量。例如 file-search/search/search-slot。
Receiver connecttargetAgentId、capabilityId、operation、demands指定请求连接哪个 provider、执行哪个 operation、需要多少 resource。
Consoleenabled、username、passwordEnvConsole 是可选观察/配置面。密码值放环境变量，配置文件只保存变量名。
不要编辑 internal.toml：它保存 PID、generation、实际端口、accepted/effective config、Console 状态和恢复信息。它由 runtime 原子生成和更新。改它不能替代修改 config.toml，也不能绕过 generation 或 CAS 检查。
第 1 步

构建可安装包

安装依赖，再生成 final 模式的包与它的身份 receipt。

pnpm install --frozen-lockfile
pnpm build:governance

产物：generated/modules/teams-source/lib
身份：generated/modules/teams-source/package-receipt.json 里的 head_commit / base_commit / content_sha256。

第 2 步

打包并安装到源码树外

用真实 tarball 安装。这一步证明包可以离开源码树运行。

npm pack generated/modules/teams-source/lib \
  --pack-destination /tmp/at-pack --json

npm install --prefix /tmp/at-prefix --no-audit --no-fund \
  --no-package-lock --no-save /tmp/at-pack/agentteams-0.1.0.tgz

可执行文件：/tmp/at-prefix/node_modules/.bin/agentteams

第 3 步

首次运行

用户只写一份可编辑配置。系统状态放在 internal.toml，用户不改。

agentteams init   --config ~/.agentteams/config.toml
agentteams start  --config ~/.agentteams/config.toml
agentteams status --config ~/.agentteams/config.toml
agentteams console start --config ~/.agentteams/config.toml
agentteams stop   --config ~/.agentteams/config.toml --generation <n>

Console 是可选的观察面。关闭 Console 后，新的 Agent Work 仍然成功。

集成与回执

git push origin main
git ls-remote origin refs/heads/main

远端返回的 SHA 必须等于本地 git rev-parse HEAD。本地干净检查用 git status --short，输出为空才算干净。

分层测试阶梯

按风险选层，不逐次跑全套。提交动作本身不触发整套测试。

跑最终验收

这是「安装后的真实业务入口」验收。它从一个安装包跑完 14 个 case，覆盖 U1–U7 与 D3/D4。

pnpm build:governance

node scripts/blackbox-user-mvp.mjs --case all \
  --package generated/modules/teams-source/lib \
  --evidence-dir /tmp/at-evidence/all \
  --receipt /tmp/at-evidence/all.receipt.json

退出码怎么读

  • 0 全部通过
  • 1 有 case 失败
  • 2 有 case 未验证（环境缺前置）

receipt 里的 exit.failed 与 exit.unverified 分别列出失败和未验证的 case。

只看一个 case

node scripts/blackbox-user-mvp.mjs --list
node scripts/blackbox-user-mvp.mjs --case BB04 \
  --package generated/modules/teams-source/lib \
  --receipt /tmp/at-evidence/bb04.receipt.json

先 --list 看 case 编号，再用 --case 单选或多选（逗号分隔）。

每个 case 做什么：功能、样例、通过条件

下面不是标签汇总，而是每个功能的真实用户样例、主要动作和必须看到的结果。每个 case 都会在证据目录写出命令、stdout、stderr、退出码和业务回执。

case功能样例测试动作通过条件
BB01安装包 / Console 静态资源npm pack/install 到源码树外；执行 init、start、status、Console 资产与认证检查。安装目录可运行；静态页、entry、icon 返回正确；未授权请求 401；自有进程可清理。
BB02两 daemon 本地 bridge只用 ~/.agentteams/config.toml 启动 provider/receiver；检查 register、discover、generation、restart。两 daemon 发现对端；generation 正确；restart 后旧 generation 被拒绝；没有 Console 也可工作。
BB03浏览器能力与容量真实 Camo 浏览器启动；发布 file-search@1 与 search-slot；执行真实 search。browser lifecycle 成功；service/resource/capacity 对外一致；结果包含匹配文件；容量耗尽时显式失败。
BB04新 Work submit/query提交 marker-alpha 与 marker-beta 两个请求；随后 query 原请求。两次得到不同 work/request identity 和不同真实结果；query 返回原业务结果，但不重新执行 Work。
BB05Work 拒绝矩阵使用未知 capability、错误 binding、无效 payload 等输入提交 Work。返回 typed error；不创建错误 Work；不偷偷 fallback、重放或吞掉错误。
BB06持久浏览器 Work保持真实浏览器上下文，连续执行需要容量的 Work，并检查 provider ledger。容量内请求成功；超过容量显式拒绝；close/dispose 后容量归还，不能泄漏 channel。
BB07未知请求与恢复查询先创建并打开 Work，再 query 不存在的 request/work identity。返回 typed unknown；查询不重新执行 agentWork.request/propose；ledger 数量不增加。
BB08配置 generation / stale提交当前 generation；再用旧 launcher/provider generation 提交；最后提交新 generation。旧 generation 明确拒绝且无副作用；新 generation 成功；错误包含 typed code。
BB09Console 生命周期与离线 Work启动真实 installed Console；访问浏览器 UI；stop Console；关闭后提交新 Work；再 restart。UI/auth 正常；Console listener 真正消失；Console 停止不影响新 Work；禁用 Console 时 start 明确拒绝。
BB10显式 provider/model Session通过 Console/Session 入口选择明确 provider、model；检查 projection、CAS 与 owner。provider/model 绑定准确；stale revision 返回 REVISION_CONFLICT 且状态不变；资源归属不串线。
BB11SDK Work 与 compile 负例通过安装后的 SDK/DAGpipe Work 入口执行；再提交非法 graph/operator 输入。合法 Work 经过 Operators → compile → immutable graph → Runtime；非法输入在 compile 边界失败。
BB12Session message/tool/permission/cancel真实 managed OpenCode 发送 message；触发 tool；发起 permission approve/reject；执行 cancel/restart。message、tool、permission、cancel 状态真实投影；未确认取消保持 unknown；restart 后旧 owner 不可写。
BB13治理失败恢复与失效先注入一次 exit 86；再运行 recovery、re-entry、idempotent、source/graph/config/artifact/evidence 变更。有效前置阶段复用；后继正确失效；真实 verify/smoke 失败保留；恢复不能伪造 PASS。
BB14失败启动 / stop / 资源回收重复 start、错误 generation stop、stale generation recovery；检查 daemon、Console、OpenCode 子进程。重复 start 明确失败；正确 generation 可 stop；stale 不误杀；owned process、socket、临时目录最终清零。
推荐阅读顺序：先运行 BB01 验证安装，接着 BB02/BB03 验证 daemon 与 provider，再运行 BB04–BB08 验证 Work/config，BB09–BB12 验证 Console/Session，最后运行 BB13/BB14 验证恢复、失败和资源终点。

三条已知边界

1. BB13 内部门禁有一次负荷抖动。 在 68c7fbe 的重跑里，BB13 克隆内的 pnpm verify 有 1/776 例失败： runtime/managed-opencode-session.spec.ts 的真实 OpenCode 往返用例实测 11.92 s，超过它自己的 10 s 预算。 该用例单独跑三次是 1.95 / 1.99 / 1.95 s，且在更早的 BB13（8 次 verify）里全通过。 这是满负荷下的时序敏感，不是产品缺陷。超时与断言都未放宽；既有 issue 5abd96e 继续跟踪。
2. 包内容哈希跨构建不可复现。 同一提交连续三次 pnpm build:governance 得到三个不同的 content_sha256。 逐文件比对定位到只有 runtime/dagpipe/bin/darwin-arm64/agentteams-dagpipe-runner 与其 manifest 每次不同，原因是本地 Rust 链接产物非确定（macOS 链接 UUID）。 所以「同一个安装包」由验收 receipt 绑定的那次产物加候选提交界定，不能用跨构建哈希比较。
3. Relay 路径仍有一个 open P1。 issue 4e04166（Relay admission grant 到期会终止进行中的浏览器 Work）未收口。 它属于 Relay 路径；已交付的本地 Phase 1 路径由 BB03/BB06 的真实浏览器 Work 覆盖并通过。
